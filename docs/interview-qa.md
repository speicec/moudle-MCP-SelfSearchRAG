# 面试技术问答话术

## 项目概述（30秒开场）

> 这是一个增强型多模态RAG系统，核心解决两个痛点：
> 1. 传统RAG固定切分导致检索碎片化
> 2. 扫描文档/图表无法被理解检索
> 技术栈：TypeScript + React + DeepSeek + PaddleOCR + qwen3-vl-flash

---

## Q1: 为什么选择语义分块而不是固定长度切分？

### 问题分析

传统固定切分的核心问题：
- "我们假设一个场景：一段代码说明有300字，传统切分在256处断开。
  结果：后半部分被切到下一个chunk，检索时只命中前半部分。
  用户看到的是'代码实现采用了...'，但看不到'工厂模式的优势是...'"

### 解决方案核心洞察

> "好的数据结构消除特殊情况。"

- 不是'切割文本'，而是'识别语义边界'
- 用embedding相似度计算相邻句子，相似度突然下降（断崖）= 语义主题切换点
- 数据结构思维：不是简单的"切分"，而是建立语义边界列表

### 实测效果

- 检索命中率提升约30%（用户实际感知）
- 消除'切到一半'的边界情况

## Q2: Small-to-Big检索为什么比直接检索大块更有效？

### 数据结构设计

> "我们用父子层级关系，不是单一尺寸chunk。"

```
        ┌─────────────────────────────────────────┐
        │          Parent Chunk (大块)             │
        │      完整语义单元 ≈ 1000-2000 tokens     │
        │                                         │
        │  ┌─────────┐ ┌─────────┐ ┌─────────┐   │
        │  │ Child 1 │ │ Child 2 │ │ Child 3 │   │
        │  │ (小块)  │ │ (小块)  │ │ (小块)  │   │
        │  │200-400  │ │200-400  │ │200-400  │   │
        │  │ tokens  │ │ tokens  │ │ tokens  │   │
        │  └─────────┘ └─────────┘ └─────────┘   │
        └─────────────────────────────────────────┘
```

### 两个阶段的本质

- **Phase 1 (小块检索)**：精准定位——embedding在高维空间的匹配精度
- **Phase 2 (父块展开)**：完整上下文——用户需要的不是碎片，是完整语义单元

### 类比解释

> "就像图书馆找书：先用索引找到章节位置（精准），再展开整章阅读（完整）。"

### 为什么不直接检索大块？

- 大块embedding会'稀释'关键信息
- 小块能精准命中，但碎片对用户无意义
- 两阶段设计是'精准定位 + 完整交付'的最佳平衡

## Q3: 断崖检测算法的具体实现？

### 算法五步

```
输入: Embedding序列 [e1, e2, ..., en]
输出: 语义边界位置列表

算法:
1. 计算相邻相似度: sim_i = cosine(e_i, e_{i+1})
2. 找候选点: candidates = {i | sim_i < threshold (0.7)}
3. 验证梯度: |sim_i - sim_{i-1}| > gradientThreshold (0.15)
4. 滤噪: 要求 minCliffWidth (2) 个相邻候选点
5. 选边界: 相邻断崖选梯度最大者
```

### 关键参数解释

| 参数 | 默认值 | 作用 |
|------|--------|------|
| similarityThreshold | 0.7 | 低于此值认为有断崖 |
| gradientThreshold | 0.15 | 相似度下降幅度足够大 |
| minCliffWidth | 2 | 防止单点噪声 |

### 置信度计算

- gradient权重60%，width权重40%
- 断崖越'陡峭'、越'宽'，置信度越高
- 公式：confidence = 0.6 * normalizedGradient + 0.4 * normalizedWidth

## Q4: 图片PDF处理的技术选型？为什么用PaddleOCR而不是Tesseract？

### 核心需求

1. **版面分析**：识别bbox + blockType (text/table/figure/formula)
2. **中文支持**：扫描文档多为中文

### PaddleOCR优势

- **PP-Structure**：原生支持版面分析，输出带bbox的结构化内容
- **中文优化**：PaddlePaddle团队对中文场景深度优化
- **开源免费**：无API调用成本

### Tesseract局限

- 主要是OCR，版面分析能力弱
- 中文需要额外语言包，效果不如国产方案

### 技术选型原则

> "实用主义。解决实际问题，不是追求理论完美。"

扫描文档在企业大量存在，这是真实痛点。

## Q5: VLM增强的实现流程？为什么不直接用OCR输出？

### OCR输出的局限

- OCR版面分析只输出：blockType + bbox + confidence
- table/figure/formula类型只有位置，没有内容理解
- 用户检索"增长率"无法命中图表块（因为图表只是'一张图片'）

### VLM增强流程

```
1. OCR识别块类型和bbox
2. 按 bbox裁剪原图 → 提取图片Buffer
3. 转Base64 → 调用 qwen3-vl-flash
4. VLM输出：Markdown表格/图表描述/公式LaTeX
5. 存入chunk → 可被关键词检索
```

### 选择qwen3-vl-flash原因

- 阿里云DashScope，国内访问稳定
- 速度快（flash系列），单表格处理<3秒
- 支持中文场景，表格/图表理解效果好

### 关键设计决策

- 'Parse阶段增强'，不是'检索阶段实时增强'
- VLM结果直接存入索引，支持关键词检索
- 与现有流程兼容（enableVlm配置开关）

## Q6: Harness架构的设计思想？

### 核心概念

| 概念 | 定义 |
|------|------|
| Harness | 编排器，协调Pipeline执行 |
| Stage | 处理阶段（如Parse、Chunk、Embed） |
| Plugin | 单一职责处理单元 |

### 设计原则

> "消除特殊情况。所有处理逻辑都是Plugin，没有'特殊模块'。"

- 可插拔：每个Stage可配置多个Plugin
- 事件驱动：Hooks机制（preExecution、postExecution、onError）

### 实际应用示例

```
Parse Stage: PdfParser Plugin → OcrPlugin → VlmPlugin
Chunk Stage: SemanticChunker Plugin → QualityFilter Plugin
Embed Stage: EmbeddingPlugin → CachePlugin
```

### 扩展性体现

- 新增处理能力只需实现Plugin接口
- 不修改Harness核心代码

## Q8: 本项目最大的技术挑战是什么？

### 挑战一：语义边界检测的准确性

**问题**：如何区分真正的语义切换和噪声？

**解决**：
- 梯度验证：要求相似度下降幅度足够大
- 宽度滤噪：要求连续多个候选点
- 窗口聚合：滑动窗口计算embedding，减少单句波动

### 挑战二：多模态内容的统一检索

**问题**：文本和图片如何在一个检索系统中共存？

**解决**：
- 双轨嵌入：文本Embedding + CLIP图像Embedding
- 融合检索：语义检索 + 关键词检索混合（权重0.7/0.3）
- VLM转换：图片内容→文本描述→存入索引

## Q9: 如果要扩展这个系统，你会怎么设计？

### 潜在扩展方向

1. **分布式检索**
   - 当前是单机内存存储
   - 扩展：向量数据库（Milvus/Qdrant）+ Redis缓存

2. **增量索引**
   - 当前是全量处理
   - 扩展：只处理新增/修改的文档

3. **多租户支持**
   - 当前是单用户
   - 扩展：DocumentStore增加userId字段

### 设计原则

> "不破坏用户空间！向后兼容是铁律。"

- 新功能通过Plugin机制添加，不修改核心
- 配置开关控制，默认关闭新功能
