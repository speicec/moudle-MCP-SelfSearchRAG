# QA-3: topK是什么？怎么设置合适的topK？如何保证答案在召回文档中？

## 问题背景

> "topK是什么，怎么设置合适的top-k，这个项目是怎么设置top-k的，你怎么确定问题的答案一定就在召回的文档中"

---

## topK的定义

```
topK = 最终返回给用户的父块数量
     ≠ 小块检索数量
     ≠ 去重前的候选数量
```

**配置中的默认值**：

| 层级 | 参数位置 | 默认值 |
|------|----------|--------|
| 配置层 | `DEFAULT_RETRIEVAL_CONFIG.topK` | 10 |
| API层 | `chat routes` 请求参数 | 5 |

```
src/chunking/config.ts:146
DEFAULT_RETRIEVAL_CONFIG = {
  topK: 10,                    // 配置默认值
  similarityThreshold: 0.5,    // 相似度门槛
  maxContextTokens: 4000,      // 上下文Token上限
}

src/server/routes/chat.ts:25
const { topK = 5 } = request.body;  // API请求默认值
```

## 完整的检索流程（topK生效位置）

```
┌─────────────────────────────────────────────────────────────────────┐
│                   Small-to-Big 检索流程                              │
└─────────────────────────────────────────────────────────────────────┘

Phase 1: 小块检索
──────────────────────────────────
queryEmbedding = embed(query)
smallChunks = getAllSmallChunks()    // 假设1000个小块
results = []
for chunk in smallChunks:
    similarity = cosine(queryEmbedding, chunk.embedding)
    results.push({chunk, similarity})
sorted = sortBySimilarity(results)   // 按相似度降序

         ↓
         │  候选池: 1000个小块（全部参与排序）
         │  没有topK限制在这里
         ↓

Phase 2: 相似度过滤
──────────────────────────────────
filtered = sorted.filter(r => r.similarity >= 0.5)

         ↓
         │  假设过滤后剩200个小块
         │  相似度门槛是第一道筛选
         ↓

Phase 3: 父块展开 + 去重
──────────────────────────────────
expanded = filtered.map(r => getParent(r.smallChunkId))
deduplicated = expanded.filter(uniqueByParentId)

         ↓
         │  假设200个小块 → 50个父块（去重）
         │  同一父块的多个子块只保留一个
         ↓

Phase 4: topK截断 ← topK在这里生效
──────────────────────────────────
limited = deduplicated.slice(0, topK)

         ↓
         │  最终返回: topK个父块
         │  默认5个（API层）或10个（配置层）
         ↓

Phase 5: Token截断（第二道筛选）
──────────────────────────────────
context = assembleContext(limited)
          按 maxContextTokens=4000 截断
```

**关键洞察**：topK不是"检索多少个"，而是"返回多少个"。

## 怎么设置合适的topK？

这是个**经验值**问题，没有理论最优解。

```
┌─────────────────────────────────────────────────────────────────────┐
│                      topK 设置考量                                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  topK太小 (1-3):                                                    │
│  ────────────────                                                   │
│  ✓ Token消耗低，响应快                                              │
│  ✗ 漏掉相关文档概率高                                               │
│  ✗ 答案可能不在召回范围内                                           │
│                                                                     │
│  topK适中 (5-10):                                                   │
│  ────────────────                                                   │
│  ✓ 平衡召回率和精确度                                               │
│  ✓ 大多数场景够用                                                  │
│  ✗ 可能有冗余上下文                                                │
│                                                                     │
│  topK太大 (20-50):                                                  │
│  ────────────────                                                   │
│  ✓ 召回率最高，漏掉概率最低                                         │
│  ✗ Token消耗大，成本高                                             │
│  ✗ 噪声增多，LLM可能被干扰                                         │
│  ✗ 响应延迟增加                                                    │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 本项目 topK=5 的设计考量

```
默认 topK=5 (API层) 的理由
─────────────────────────────────────────

1. maxContextTokens=4000 的约束
   - 5个父块 × 平均800 tokens = 4000
   - 恰好填满上下文窗口，不浪费

2. Small-to-Big 的精准性
   - 小块检索精准定位
   - 父块展开提供完整上下文
   - 命中质量高，不需要更多候选

3. 实用主义
   - 企业文档场景，答案通常集中在一个段落
   - 5个父块覆盖足够广
```

## 核心问题：如何保证答案一定在召回文档中？

**答案是：无法保证。**

这是RAG系统的根本假设缺陷。

```
┌─────────────────────────────────────────────────────────────────────┐
│                    RAG 的根本假设                                     │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  假设：答案存在于已索引的文档库中                                    │
│                                                                     │
│  现实情况：                                                          │
│  ─────────────                                                      │
│                                                                     │
│  情况A: 答案确实在文档中 → 检索能找到                                │
│         └───────────────────────────────────                        │
│         需要条件：                                                   │
│         1. 文档已被索引                                              │
│         2. Query和文档语义匹配                                       │
│         3. 相似度 > threshold                                        │
│         4. 排名在 topK 以内                                          │
│                                                                     │
│  情况B: 答案在文档中，但检索不到                                     │
│         └───────────────────────────────────                        │
│         原因：                                                       │
│         1. 语义漂移：Query表达和文档表达不一致                        │
│            用户问："性能优化"                                        │
│            文档写："速度提升方案"                                    │
│            embedding相似度低 → 漏掉                                  │
│                                                                     │
│         2. 分块边界问题                                              │
│            答案跨两个chunk → 被切散                                  │
│            任意单个chunk都不完整                                     │
│                                                                     │
│         3. 相似度门槛太高                                            │
│            threshold=0.5                                            │
│            实际答案相似度=0.45 → 被过滤                              │
│                                                                     │
│         4. topK太小                                                  │
│            答案排名第6                                               │
│            topK=5 → 被截断                                          │
│                                                                     │
│  情况C: 答案根本不在文档库中                                         │
│         └───────────────────────────────────                        │
│         用户问的内容从未被记录                                       │
│         RAG系统无能为力                                              │
│         LLM只能依赖自身知识回答                                      │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## 当前系统的应对机制

```typescript
// src/chunking/small-to-big-retriever.ts:156-176

// 机制1: 相似度门槛
filteredResults = smallResults.filter(
  r => r.similarityScore >= this.config.similarityThreshold  // 0.5
);

// 机制2: Fallback策略
if (filteredResults.length === 0 && this.config.enableFallback) {
  // 直接检索父块，降低门槛到0.4
  fallbackResults = this.fallbackSearch(queryEmbedding)
                     .filter(r => r.similarityScore >= 0.4);
  return fallbackResults;
}

// 机制3: 空结果处理（在chat.ts）
if (chunkCount.small === 0) {
  return reply.status(200).send({
    message: 'No documents have been processed. Upload documents first.',
  });
}
```

## 设计改进建议

### 正确的做法：不假设，而是验证

```
不假设答案一定在召回中
而是设计系统让它能承认"不知道"

─────────────────────────────────────────

1. 置信度阈值
   - 所有召回结果相似度 < 0.5 → 返回"未找到相关信息"
   - 不是强行给5个低质量结果

2. LLM注入提示
   - Context: "以下是检索到的相关信息（置信度：低）"
   - LLM知道这是低置信度，可以谨慎回答

3. 检索失败反馈
   - 用户反馈"答案不对" → 记录查询
   - 分析为什么漏掉 → 调整参数或改进文档
```

### 数据结构改进

```
"数据结构思维"
─────────────────────────────────────────
不是"调topK参数"
而是"设计置信度数据结构"

每个检索结果应该携带：
{
  content: "...",
  similarityScore: 0.72,
  confidence: "high" | "medium" | "low",
  whyMatched: "semantic similarity | keyword match | fallback",
}

LLM根据置信度决定回答策略：
- high confidence → 直接引用
- medium confidence → 谨慎总结
- low confidence → "我找到了一些可能相关的信息，但不确定..."
```

## 面试回答模板

### 简短版（30秒）

> topK是最终返回给用户的父块数量，这个项目默认设为5。选择5是因为结合Small-to-Big检索策略和4000 token上下文限制，5个父块恰好能覆盖足够信息又不浪费Token。至于答案是否一定在召回中，我们实际上无法确定——这是RAG的根本假设缺陷。当前系统通过相似度门槛和Fallback机制尽量提高召回率，但缺少召回率评估和"我不知道"机制来处理答案不在文档库的情况。

### 深入版（展开）

> topK的本质是"最终返回多少个结果"，而不是"检索多少个候选"。在Small-to-Big策略里，topK是在父块去重后截断的，所以实际参与排序的小块数量远大于topK。
> 
> 这个项目默认topK=5的设计考量是实用主义的：4000 token的上下文窗口限制，加上Small-to-Big的精准性，5个父块在大多数企业文档场景够用。
> 
> 但更核心的问题是：你怎么保证答案一定在召回的topK个结果里？答案是：**无法保证**。这是RAG系统的根本假设缺陷——我们假设答案存在于文档库中，但无法验证。
> 
> 可能漏掉的原因有四种：语义漂移（用户表达和文档表达不一致）、分块边界问题（答案被切散）、相似度门槛过高、topK截断过早。当前系统只有相似度门槛和Fallback两种机制应对，缺少召回率评估、查询扩展、重排序、以及最关键的"我不知道"机制。
> 
> 如果用户问的内容不在文档库中，或者召回相似度都很低，LLM不应该强行编造，而是应该能说"我没有找到相关信息"。这需要给每个检索结果附加置信度元数据，让LLM根据置信度决定回答策略——这是这个系统目前缺失的设计。
