## 特质一：测试先行（Test First）

### 定义

**先写测试，再写功能。**

不是"功能完成后补测试"，而是"测试定义功能"。

### 为什么重要

| 问题 | 测试先行的解决 |
|------|---------------|
| 功能偏离需求 | 测试定义了正确行为 |
| 无法验证完成 | 测试通过=完成 |
| 回归无法发现 | 测试保护已有功能 |
| AI盲目实现 | AI读测试知道预期 |

### AI行为规范

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│   测试先行的AI行为                                                              │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│   IMPLEMENT前：                                                                 │
│   ───────────────────────────────────────────────────────────────────────       │
│   1. 检查是否有测试文件                                                         │
│   2. 如果没有，先创建测试                                                        │
│   3. 测试定义预期行为                                                            │
│   4. 再实现功能                                                                  │
│                                                                                 │
│   流程：                                                                         │
│   ───────────────────────────────────────────────────────────────────────       │
│   ✓ 读需求 → 写测试 → 实现功能 → 测试通过                                       │
│   ❌ 读需求 → 实现功能 → 写测试（如果时间允许）                                  │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 反例

```
❌ 错误做法：

AI: 实现语义分块功能
   [写代码...]
   [写代码...]
   [代码完成]
   用户: 测试呢？
   AI: 还没写测试...
```

后果：
- 代码可能偏离需求
- 无法验证是否正确
- 未来改动可能破坏功能

### 正例

```
✅ 正确做法：

AI: 实现语义分块功能
   先创建测试文件 semantic-chunker.test.ts
   
   测试用例：
   - 测试单一断崖检测
   - 测试多断崖处理
   - 测试无断崖fallback
   
   [写测试...]
   [测试定义预期行为]
   
   现在实现功能：
   [写代码...]
   
   运行测试：
   ✓ 测试通过
   
   标记任务完成
```

### 测试先行在tasks.md中的体现

```markdown
## 2. 检测算法

- [ ] 2.0 创建 `cliff-detector.test.ts` 测试文件
- [ ] 2.1 实现候选点筛选
- [ ] 2.2 实现梯度验证
- [ ] 2.3 实现宽度滤噪

## 4. Verification

- [ ] 4.0 运行 `npm test`，所有测试通过
```

## 特质二：主动测试（Active Test）

### 定义

**完成后主动运行验证，不是等用户要求。**

[x] 标记的前提是测试通过，不是"我写了代码"。

### 为什么重要

| 问题 | 主动测试的解决 |
|------|---------------|
| "我觉得完成了" | 实际运行验证 |
| 假完成标记 | 标记前必须测试 |
| Bug进入下游 | 测试拦截问题 |
| 无法追溯 | Notes记录实测结果 |

### AI行为规范

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│   主动测试的AI行为                                                              │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│   标记 [x] 前必须：                                                             │
│   ───────────────────────────────────────────────────────────────────────       │
│   1. 运行相关测试                                                               │
│   2. 观察测试结果                                                               │
│   3. 确认测试通过                                                               │
│   4. 才能标记 [x]                                                               │
│   5. 记录 Notes                                                                 │
│                                                                                 │
│   流程：                                                                         │
│   ───────────────────────────────────────────────────────────────────────       │
│   ✓ 实现代码 → 运行测试 → 测试通过 → 标记[x] → 记录Notes                        │
│   ❌ 实现代码 → 标记[x] → (没有运行测试)                                        │
│                                                                                 │
│   如果测试失败：                                                                 │
│   ───────────────────────────────────────────────────────────────────────       │
│   ✓ 修复问题 → 重新测试 → 通过 → 标记[x]                                        │
│   ❌ 标记[x] → 说"可能有小问题"                                                 │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 反例

```
❌ 错误做法：

AI: 任务2.1完成
   [标记 - [x] 2.1]
   
用户: 测试了吗？
AI: 还没有，但我觉得代码是对的...
```

后果：
- 可能有小bug
- 假完成污染下游任务
- 无法追溯真实状态

### 正例

```
✅ 正确做法：

AI: 任务2.1完成，运行测试
   
   [运行 npm test cliff-detector]
   
   测试结果：
   ✓ 候选点筛选: 通过
   ✓ 边界识别: 通过
   
   [标记 - [x] 2.1]
   
   Notes: 2.1: 测试通过，候选点筛选正确 ✓
```

### Verification任务的设计

```markdown
## 6. Verification

每个验证任务必须有：
- [ ] 6.1 运行 `npm run setup` → 进度条显示
- [ ] 6.2 启动服务器 → WebSocket连接
- [ ] 6.3 上传文档 → 响应时间 <0.1s

## Notes

- 6.1: 进度条显示 ✓
- 6.2: WebSocket连接 ✓  
- 6.3: 响应时间 0.011s ✓
```

## 特质三：遵循规范（Follow Specs）

### 定义

**遵守项目已有的规范和模式，不擅自创新。**

### 为什么重要

| 问题 | 遵循规范的解决 |
|------|---------------|
| 代码风格不一致 | 遵守已有风格 |
| 重复发明轮子 | 使用已有模式 |
| 破坏现有架构 | 遵守架构规范 |
| AI猜测模式 | 读规范文档 |

### AI行为规范

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│   遵循规范的AI行为                                                              │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│   IMPLEMENT前必须：                                                             │
│   ───────────────────────────────────────────────────────────────────────       │
│   1. 读 CLAUDE.md（如果有）                                                     │
│   2. 读 openspec/specs/（如果有相关能力规范）                                   │
│   3. 读类似功能的现有代码                                                       │
│   4. 理解项目模式和风格                                                         │
│                                                                                 │
│   遵循内容：                                                                     │
│   ───────────────────────────────────────────────────────────────────────       │
│   • 命名规范：变量/函数/文件的命名方式                                           │
│   • 代码风格：缩进、注释、import方式                                             │
│   • 架构模式：service/handler/store分层                                         │
│   • 错误处理：项目如何处理异常                                                   │
│   • 测试风格：测试文件结构和命名                                                 │
│                                                                                 │
│   流程：                                                                         │
│   ───────────────────────────────────────────────────────────────────────       │
│   ✓ 读规范 → 读类似代码 → 遵循模式实现                                          │
│   ❌ 直接实现 → 使用自己习惯的模式                                               │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 反例

```
❌ 错误做法：

AI: 创建新服务
   [使用自己的命名风格]
   [使用自己喜欢的错误处理方式]
   
用户: 这不符合项目风格
AI: 我不知道有风格规范...
```

后果：
- 代码风格不一致
- 难以维护
- 破坏架构一致性

### 正例

```
✅ 正确做法：

AI: 创建新服务
   先读现有服务代码：LLMGenerationService.ts
   
   观察模式：
   - 命名：XXXService
   - 依赖注入：constructor(private config: Config)
   - 错误处理：try-catch + logger.error
   
   遵循模式创建新服务
```

### 规范文档示例

```markdown
# CLAUDE.md（项目规范示例）

## 命名规范

- 文件：kebab-case（semantic-chunker.ts）
- 类：PascalCase（SemanticChunker）
- 函数：camelCase（detectCliffs）
- 常量：UPPER_CASE（MAX_CHUNK_SIZE）

## 架构模式

- 服务层：src/services/
- 处理器：src/handlers/
- 存储：src/stores/
- 测试：__tests__/（与源码同级）

## 错误处理

- 使用 try-catch
- 错误日志：logger.error('[ServiceName]', error)
- 用户错误：返回 { success: false, error: 'message' }
```

## 特质四：诚实认真查询（Honest Query）

### 定义

**不确定就先查证，不猜测。**

宁可多花时间查证，不要基于错误假设实现。

### 为什么重要

| 问题 | 诚实查询的解决 |
|------|---------------|
| 基于错误假设实现 | 先查证再实现 |
| API理解错误 | 读文档/源码 |
| 破坏已有功能 | 查现有实现 |
| 假完成 | 查实际运行结果 |

### AI行为规范

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│   诚实认真查询的AI行为                                                          │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│   遇到不确定时：                                                                 │
│   ───────────────────────────────────────────────────────────────────────       │
│   1. 停止实现                                                                   │
│   2. 使用工具查证                                                               │
│      • Read：读相关代码                                                         │
│      • Grep：搜索关键词                                                         │
│      • Bash：运行命令查看                                                       │
│   3. 获得确定信息                                                               │
│   4. 再继续实现                                                                 │
│                                                                                 │
│   不确定场景：                                                                   │
│   ───────────────────────────────────────────────────────────────────────       │
│   • 参数值不确定 → grep查找类似用法                                             │
│   • API行为不确定 → 读源码/文档                                                 │
│   • 文件位置不确定 → glob搜索                                                   │
│   • 依赖版本不确定 → 读package.json                                             │
│                                                                                 │
│   流程：                                                                         │
│   ───────────────────────────────────────────────────────────────────────       │
│   ✓ 遇到不确定 → 查证 → 确定 → 继续                                             │
│   ❌ 遇到不确定 → 猜测 → 可能错误 → 继续                                        │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 反例

```
❌ 错误做法：

AI: 需要调用embedding服务
   [猜测API是 embed(text)]
   [猜测返回格式是 {vector: [...]}]
   
   [实现代码使用猜测的API]
   
   [代码失败]
AI: API调用失败，可能我猜错了...
```

后果：
- 基于错误假设实现
- 浪费时间调试
- 可能引入bug

### 正例

```
✅ 正确做法：

AI: 需要调用embedding服务
   不确定API签名，先查证
   
   [Grep: "embedding service"]
   [Read: src/embedding/embedding-service.ts]
   
   发现：
   - API: generateEmbedding(text: string): Promise<number[]>
   - 返回直接是数组，不是对象
   
   [使用正确API实现]
   
   ✓ 成功
```

### 查证场景示例

| 不确定 | 查证方法 |
|--------|---------|
| 函数存在吗？ | `Grep pattern: "functionName"` |
| 函数签名？ | `Read file.ts` 找到函数定义 |
| 参数默认值？ | `Grep pattern: "paramName"` |
| 依赖版本？ | `Read package.json` |
| 配置项？ | `Read config.ts` 或 `Grep pattern: "CONFIG"` |
| 文件位置？ | `Glob pattern: "**/*name*"` |

## 特质五：谨慎重构（Safe Refactor）

### 定义

**小步重构，不破坏。**

每次改动保持最小，验证后再继续。

### 为什么重要

| 问题 | 谨慎重构的解决 |
|------|---------------|
| 大改动失控 | 小步迭代 |
| 破坏现有功能 | 每步验证 |
| 无法回退 | 保持接口 |
| AI激进重构 | 强制小步 |

### AI行为规范

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│   谨慎重构的AI行为                                                              │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│   重构原则：                                                                     │
│   ───────────────────────────────────────────────────────────────────────       │
│   1. 保持接口不变                                                               │
│   2. 单文件修改                                                                 │
│   3. 每步验证                                                                   │
│   4. 不删除代码（先标记deprecated）                                             │
│                                                                                 │
│   重构流程：                                                                     │
│   ───────────────────────────────────────────────────────────────────────       │
│   Step 1: 分析现有代码                                                          │
│   Step 2: 设计新结构（保持接口）                                                 │
│   Step 3: 单文件迁移                                                            │
│   Step 4: 验证不破坏                                                            │
│   Step 5: 继续下一个                                                            │
│                                                                                 │
│   禁止：                                                                         │
│   ───────────────────────────────────────────────────────────────────────       │
│   ❌ 同时修改多个文件                                                           │
│   ❌ 修改接口签名                                                               │
│   ❌ 删除现有代码（未deprecated）                                               │
│   ❌ 未验证就继续                                                               │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 反例

```
❌ 错误做法：

AI: 重构检索模块
   [同时修改5个文件]
   [修改接口签名]
   [删除旧代码]
   
   [运行测试]
   ❌ 大量测试失败
   
AI: 需要修复所有调用方...
```

后果：
- 破坏面太大
- 难以定位问题
- 无法回退
- 测试全面失败

### 正例

```
✅ 正确做法：

AI: 重构检索模块
   先设计：保持接口不变
   
   Step 1: 重构 Retriever.ts
   [修改内部实现]
   [保持公开方法签名]
   [运行测试] ✓
   
   Step 2: 重构 SearchEngine.ts
   [修改内部实现]
   [保持接口]
   [运行测试] ✓
   
   ... 继续单文件迭代
```

### 重构任务示例

```markdown
## 1. 重构准备

- [ ] 1.1 分析现有代码结构
- [ ] 1.2 设计新结构（保持接口）
- [ ] 1.3 确定重构步骤

## 2. 逐文件重构

- [ ] 2.1 重构 Retriever.ts（保持接口）
- [ ] 2.2 验证：运行测试，不破坏
- [ ] 2.3 重构 SearchEngine.ts
- [ ] 2.4 验证：运行测试，不破坏
- [ ] 2.5 重构 Indexer.ts
- [ ] 2.6 验证：运行测试，不破坏

## 3. 清理

- [ ] 3.1 标记旧代码为 @deprecated
- [ ] 3.2 等待过渡期后删除

## N. Verification

- [ ] N.1 所有测试通过
- [ ] N.2 接口签名不变
- [ ] N.3 性能不下降
```
