# 四阶段工作流详解

> EXPLORE → PROPOSE → APPLY → ARCHIVE 完整流程说明

---

## Phase 1: EXPLORE（探索）

### 目的

**让问题形状自然浮现，不急于实现。**

这是方法论与传统AI编码的关键区别：探索阶段**禁止写代码**。

### AI行为规范

| 行为 | 说明 | 目的 |
|------|------|------|
| 读文件 | 用Read工具读相关代码 | 理解当前实现 |
| 画ASCII图 | 用字符画架构图 | 建立视觉理解 |
| 提问 | 用AskUserQuestion澄清 | 避免误解需求 |
| 比较方案 | 列出多种可能 | 展示trade-off |
| 不写代码 | 只读不写 | 防止冲动实现 |

### 典型对话模式

```
用户: 我想加一个语义分块功能

AI: 让我思考一下这个问题...

     ┌─────────────────────────────────────────┐
     │     当前架构：固定长度切分                 │
     ├─────────────────────────────────────────┤
     │                                         │
     │   Document → Split(512 tokens) → Chunks │
     │                                         │
     │   问题：                                  │
     │   • 语义边界被切断                        │
     │   • 检索结果碎片化                        │
     │   • 上下文不完整                          │
     │                                         │
     └─────────────────────────────────────────┘

     你想解决的核心问题是什么？
     1. 检索精度问题？
     2. 上下文完整性问题？
     3. 还是两者都要？
```

### 探索阶段产出

探索阶段**没有文件产出**，但有认知产出：

- 对问题的清晰理解
- 对架构的认知
- 对方案的选择倾向
- 对风险的预判

### 何时进入下一阶段

当以下条件满足时，可以提议进入PROPOSE阶段：

```
✓ 问题理解清晰（用户确认）
✓ 有明确的方案倾向
✓ 知道要修改哪些文件
✓ 知道主要风险点
```

AI应该主动提议：
> "这个问题我理解清楚了，想创建提案吗？"

---

## Phase 2: PROPOSE（提案）

### 目的

**将探索成果文档化，形成实施蓝图。**

### 产出物

```
openspec/changes/<变更名>/
├── proposal.md    # 为什么做、做什么、影响什么
├── design.md      # 怎么做、为什么这么选、风险是什么
├── specs/         # 具体能力的行为规范（可选）
└── tasks.md       # 原子任务列表
```

### 创建顺序（依赖关系）

```
          proposal.md
              │
              │  提供scope
              ▼
          design.md
              │
              │  提供架构
              ▼
    specs/<能力>/spec.md
              │
              │  提供验证标准
              ▼
          tasks.md
```

### 各文档作用

| 文档 | 内容 | AI利用方式 |
|------|------|-----------|
| **proposal.md** | Why/What | 防止范围蔓延 |
| **design.md** | How/Why-Not | 防止架构猜测（关键） |
| **specs/spec.md** | What-Shall | 防止行为偏离 |
| **tasks.md** | When/Verified | 防止半途而废 |

### design.md的关键性

design.md是**最重要的文档**，因为它：

1. **记录决策**：Choice + Rationale + Alternatives
2. **画架构图**：AI读图比读文字更理解
3. **定义边界**：Goals vs Non-Goals
4. **预判风险**：提前知道可能的问题

示例：
```markdown
### Decision 1: 预加载时机

**选择**: HTTP服务器启动后预加载

**理由**:
- 服务器可立即响应健康检查（Docker/K8s readiness probes）
- WebSocket可广播加载进度

**备选方案**:
1. ❌ 服务器启动前加载 → readiness probes失败
2. ❌ 并行加载 → 与首次请求竞争
```

AI读这段后：
- 知道要实现"启动后预加载"
- 知道为什么不能"启动前"
- 知道为什么不能"并行"

### tasks.md的原子化

任务必须原子化：

```markdown
## 1. 基础结构

- [ ] 1.1 创建 `src/chunking/cliff-detector.ts` 文件骨架
- [ ] 1.2 添加 `detectCliffs()` 函数签名
- [ ] 1.3 实现相似度计算逻辑

## 2. 检测算法

- [ ] 2.1 实现候选点筛选 (sim < threshold)
- [ ] 2.2 实现梯度验证 (|diff| > gradientThreshold)
- [ ] 2.3 实现宽度滤噪 (minCliffWidth)

## N. Verification

- [ ] N.1 测试单一断崖检测
- [ ] N.2 测试多断崖处理
- [ ] N.3 测试无断崖fallback
```

每个任务：
- **单文件**：只涉及一个文件
- **单功能**：只做一件事
- **可验证**：有明确成功标准

## Phase 3: APPLY（实施）

### 目的

**原子化执行，每步可验证。**

### AI行为规范

| 行为 | 说明 | 目的 |
|------|------|------|
| 读design.md | 先读架构决策 | 不猜测方案 |
| 读tasks.md | 获取任务列表 | 知道做什么 |
| 逐任务执行 | 一个一个做 | 不跳过 |
| 标记[x] | 完成后立即标记 | 进度可见 |
| 验证完成 | 标记前先验证 | 防止假完成 |
| 遇问题暂停 | 不清楚就问 | 不盲目实施 |

### 实施流程示例

```
## 实施变更: startup-preload-optimization

正在执行任务 3/7: 添加WebSocket广播

[AI读取design.md Decision 2]
[AI编写代码]

✓ 任务完成
[AI标记: - [x] 3.2]

正在执行任务 4/7: 创建前端组件

[AI遇到不清楚的地方]
暂停：前端组件应该放在哪个目录？
    1. src/frontend/components/
    2. src/components/
    
用户: 用第一个

[AI继续实施]
```

### 关键：验证后标记

[x] 标记表示**已验证完成**，不是"我写了代码"。

正确的标记流程：
```
1. 实现代码
2. 运行测试/验证命令
3. 观察结果
4. 确认成功
5. 标记 [x]
6. 记录 Notes（可选）
```

错误做法：
```
❌ 写了代码 → 直接标记 [x] → 没有运行测试
```

### 验证任务示例

```markdown
## 6. Verification

- [ ] 6.1 运行 `npm run setup` 验证进度显示
- [ ] 6.2 启动服务器验证WebSocket广播
- [ ] 6.3 上传文档验证即时响应 (应<0.1s)

## Notes

实施完成于 2026-04-20.
- 6.1: 进度条正确显示 ✓
- 6.2: WebSocket客户端连接 ✓
- 6.3: 上传返回时间 0.011s ✓
```

## Phase 4: ARCHIVE（归档）

### 目的

**保留决策历史，供未来参考。**

### 归档操作

```bash
openspec archive <变更名>
```

这会：
1. 移动变更到 `openspec/changes/archive/<日期>-<变更名>/`
2. 更新主 `openspec/specs/`（如果添加了新能力）
3. 保留所有决策文档

### 归档的价值

| 场景 | 归档文档的作用 |
|------|---------------|
| 未来AI对话 | 可引用归档决策 |
| 用户面试 | 可解释每个选择 |
| 新成员学习 | 可理解项目演进 |
| Bug排查 | 可理解设计意图 |

### 归档示例

```
openspec/changes/archive/
│
├── 2026-04-09-semantic-chunking-hierarchical-retrieval/
│   ├── proposal.md      ← 为什么需要语义分块
│   ├── design.md        ← 断崖检测算法设计决策
│   ├── specs/           ← 语义分块的行为规范
│   └── tasks.md         ← 实施过程记录
│
├── 2026-04-13-deepseek-llm-integration/
│   ├── proposal.md      ← 为什么选DeepSeek
│   ├── design.md        ← SSE→WebSocket转换决策
│   └── tasks.md         ← 实施过程
│
└── ...
```

## 阶段切换规则

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                          阶段切换条件                                            │
└─────────────────────────────────────────────────────────────────────────────────┘

    EXPLORE → PROPOSE
    ────────────────────
    ✓ 问题理解清晰
    ✓ 有方案倾向
    ✓ 用户确认可以开始
    
    PROPOSE → APPLY
    ────────────────────
    ✓ proposal.md 完成
    ✓ design.md 完成
    ✓ tasks.md 完成
    ✓ 用户确认可以实施
    
    APPLY → ARCHIVE
    ────────────────────
    ✓ 所有tasks [x]
    ✓ Verification通过
    ✓ 用户确认完成
    
    阶段回退
    ────────────────────
   任何时候都可以：
    • APPLY遇到问题 → 回退PROPOSE更新design
    • PROPOSE发现理解错误 → 回退EXPLORE重新思考
```

---

## 不强制顺序

方法论是**stance（态度）**，不是严格workflow：

- 可以直接PROPOSE（如果问题很清楚）
- 可以PROPOSE后继续EXPLORE（发现新问题）
- 可以APPLY中更新design（实现中发现问题）
- 可以不ARCHIVE（继续迭代）

关键原则：
> **先思考，再实现；先文档，再代码。**

---

## 与传统开发对比

| 活动 | 传统开发 | OpenSpec方法论 |
|------|---------|---------------|
| 理解需求 | 聊聊就开始 | EXPLORE阶段画图提问 |
| 设计方案 | 脑子里想 | PROPOSE阶段写design.md |
| 实施编码 | 一口气写完 | APPLY阶段逐任务原子执行 |
| 验证完成 | 我觉得完了 | Verification任务有标准 |
| 保存历史 | git log | ARCHIVE归档决策文档 |

方法论的价值不是"严格按步骤"，而是：
- **强制思考阶段**（EXPLORE不许写代码）
- **强制文档阶段**（PROPOSE必须写design）
- **原子执行**（APPLY逐任务）
- **决策留存**（ARCHIVE归档）
