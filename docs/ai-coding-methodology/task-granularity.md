# 任务分解原则

> 原子化任务，每步可验证

---

## 核心原则：原子化

**一个任务 = 一个文件 + 一个功能 + 可验证**

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                          任务原子化标准                                          │
└─────────────────────────────────────────────────────────────────────────────────┘

    ┌──────────────────────────────────────────────────────────────────────────────┐
    │   合格任务                          │   不合格任务                           │
    ├──────────────────────────────────────────────────────────────────────────────┤
    │   • 只涉及1个文件                   │   • 涉及多个文件                        │
    │   • 只做1个功能                     │   • 包含多个逻辑                        │
    │   • <30分钟完成                     │   • >1小时                              │
    │   • 有明确验证标准                  │   • 描述模糊                            │
    │   • 可独立完成                      │   • 依赖未完成的任务                    │
    └──────────────────────────────────────────────────────────────────────────────┘
```

---

## 分解示例

### ❌ 错误：任务太大

```markdown
- [ ] 实现语义分块功能
```

**问题**：
- AI不知道从哪开始
- 可能半途而废
- 无法验证中间步骤
- "完成了"的定义不清楚

### ✅ 正确：原子任务

```markdown
## 1. 基础结构

- [ ] 1.1 创建 `src/chunking/cliff-detector.ts` 文件骨架
- [ ] 1.2 添加 `detectCliffs()` 函数签名
- [ ] 1.3 定义 `CliffDetectorConfig` 接口

## 2. 检测算法

- [ ] 2.1 实现候选点筛选 (sim < threshold)
- [ ] 2.2 实现梯度验证 (|diff| > gradientThreshold)
- [ ] 2.3 实现宽度滤噪 (minCliffWidth)
- [ ] 2.4 实现置信度计算

## 3. 集成

- [ ] 3.1 在 `semantic-chunker.ts` 中调用 cliff-detector
- [ ] 3.2 添加配置参数传递
- [ ] 3.3 处理返回的边界列表

## 4. 验证

- [ ] 4.1 测试用例：单一断崖检测
- [ ] 4.2 测试用例：多断崖处理
- [ ] 4.3 测试用例：无断崖fallback
- [ ] 4.4 测试用例：噪声过滤
```

**优点**：
- 每个任务30分钟内
- 有明确的"完成"定义
- 验证任务独立
- 可追踪进度

## 任务编号原则

使用层级编号：

```
1. 阶段名称
   1.1 任务
   1.2 任务
   1.3 任务

2. 阶段名称
   2.1 任务
   2.2 任务

N. Verification
   N.1 验证任务
   N.2 验证任务
```

### 编号的用途

| 用途 | 说明 |
|------|------|
| 追踪进度 | "正在执行2.3" |
| 依赖关系 | "1.x完成后才能做2.x" |
| 验证对照 | "验证4.2对应算法2.2" |

---

## 任务大小判断标准

| 维度 | 合格 | 不合格 | 判断方法 |
|------|------|--------|---------|
| **文件数** | 1个 | >1个 | 任务描述是否提到多个文件 |
| **时间** | <30分钟 | >1小时 | 你能30分钟做完吗 |
| **验证** | 明确标准 | 模糊 | 有具体命令或检查项 |
| **复杂度** | 单一逻辑 | 多逻辑 | 能否一句话描述 |
| **依赖** | 无阻塞依赖 | 有阻塞 | 前面任务是否完成 |

### 自检清单

写任务时问自己：
1. 这个任务只改一个文件吗？
2. 能在30分钟内完成吗？
3. 完成后怎么验证？
4. 有依赖的任务吗？它们完成了吗？

## 验证任务的重要性

**每个变更必须有验证章节**。

### 验证任务格式

```markdown
## N. Verification

- [ ] N.1 [具体命令] + [期望结果]
- [ ] N.2 [具体命令] + [期望结果]
- [ ] N.3 [具体命令] + [期望结果]
```

### 验证任务示例

```markdown
## 6. Verification

- [ ] 6.1 运行 `npm run setup`，验证进度条显示
- [ ] 6.2 启动服务器 `npm run dev`，验证WebSocket广播
- [ ] 6.3 打开前端 http://localhost:3001，验证StartupProgress组件
- [ ] 6.4 上传测试文档，验证首次响应时间 <0.1s

## Notes

实施完成于 2026-04-20.
- 6.1: 进度条正确显示，模型名可见 ✓
- 6.2: WebSocket客户端连接，事件广播 ✓
- 6.3: StartupProgress组件渲染 ✓
- 6.4: 上传响应时间 0.011s ✓
```

### 验证任务特点

| 特点 | 说明 |
|------|------|
| **有具体命令** | `npm run X`、`curl Y` |
| **有期望结果** | `显示X`、`返回Y`、`时间<Z` |
| **可量化** | 有数字标准 |
| **记录实际结果** | Notes中记录真实值 |

## 标记 [x] 的正确方式

### 错误做法

```
❌ 写了代码 → 直接标记 [x] → 没有运行测试
```

后果：
- 代码可能有bug
- 功能可能不完整
- 无法追溯问题

### 正确做法

```
1. 实现代码
2. 运行验证命令
3. 观察结果
4. 确认符合期望
5. 标记 [x]
6. 记录 Notes（可选）
```

### 标记流程示例

```
任务: 2.1 实现候选点筛选

[AI实现代码]
[AI运行测试]
[AI观察输出]

✓ 测试通过：5个候选点正确识别

[AI标记: - [x] 2.1]
[AI记录Notes: 2.1: 候选点识别正确 ✓]
```

## 实施笔记的价值

### Notes格式

```markdown
## Notes

实施完成于 YYYY-MM-DD.
- N.1: [实际结果] ✓
- N.2: [实际结果] ✓
- N.3: [实际结果] ✓（或说明问题）
```

### Notes示例

```markdown
## Notes

实施完成于 2026-04-20.
- 6.1: 进度条正确显示，模型名和文件详情可见 ✓
- 6.2: 服务器日志显示启动序列，WebSocket客户端连接 ✓
- 6.3: 前端从服务器加载，StartupProgress渲染 ✓
- 6.4: 文档上传返回时间 0.011s（预加载后即时） ✓
```

### Notes用途

| 用途 | 说明 |
|------|------|
| **证明完成** | 不是"我觉得"，是"实测结果" |
| **记录数据** | 性能数字、实际表现 |
| **追溯问题** | 未来排查可看原始数据 |
| **面试展示** | 能说"实测响应时间0.011s" |

## 不同类型变更的任务结构

### 新功能

```markdown
## 1. 基础结构
## 2. 核心算法
## 3. 集成
## 4. 前端（如有）
## 5. API（如有）
## N. Verification
```

### Bug修复

```markdown
## 1. 问题定位
## 2. 修复实现
## 3. 验证修复
## N. Verification
```

示例：
```markdown
## 1. 问题定位

- [ ] 1.1 复现bug：流式传输页面抖动
- [ ] 1.2 定位根因：scrollIntoView频繁调用
- [ ] 1.3 确认影响：ChatWindow.tsx useEffect

## 2. 修复实现

- [ ] 2.1 修改useEffect依赖：移除currentThinking
- [ ] 2.2 添加debounce滚动
- [ ] 2.3 简化动画效果

## 3. 验证修复

- [ ] 3.1 发送测试查询，观察页面稳定性
- [ ] 3.2 确认消息完成后正确滚动
- [ ] 3.3 确认动画效果正常
```

### 重构

```markdown
## 1. 分析现有代码
## 2. 设计新结构
## 3. 小步迁移
## 4. 验证不破坏
## N. Verification
```

## 任务依赖处理

### 明确依赖

```markdown
## 1. 基础结构（无依赖）

- [ ] 1.1 创建文件
- [ ] 1.2 定义接口

## 2. 核心算法（依赖1完成）

- [ ] 2.1 实现算法（依赖1.2的接口）
- [ ] 2.2 调用1.1创建的文件
```

### 阻塞处理

如果任务A阻塞任务B：
1. 先完成A
2. 标记A为 [x]
3. 再开始B

如果A遇到问题：
1. 暂停B
2. 解决A的问题
3. 可能需要更新design

## 常见错误及修正

### 错误1：任务描述模糊

```markdown
❌ - [ ] 改进性能

✅ - [ ] 优化检索算法，响应时间从500ms降到50ms
```

### 错误2：任务太大

```markdown
❌ - [ ] 完成整个检索模块

✅ - [ ] 2.1 实现向量检索
✅ - [ ] 2.2 实现关键词检索
✅ - [ ] 2.3 实现RRF融合
```

### 错误3：缺少验证

```markdown
❌ - [ ] 添加进度显示

✅ - [ ] 5.1 创建StartupProgress组件
✅ - [ ] 5.2 验证：组件渲染，进度更新
```

### 错误4：过早标记

```markdown
❌ - [x] 实现算法（还没测试）

✅ - [ ] 实现算法
✅ - [x] 测试通过
```

## 总结：原子任务检查清单

在创建tasks.md时，对每个任务检查：

```
□ 只涉及一个文件？
□ 能在30分钟内完成？
□ 有明确的验证标准？
□ 描述具体，不模糊？
□ 依赖的任务已完成？
□ 编号清晰？
```

满足所有条件，才是合格的原子任务。
