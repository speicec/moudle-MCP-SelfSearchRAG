# 决策记录方法

> Choice + Rationale + Alternatives 决策文档化方法论

---

## 为什么决策文档化是关键

AI编码的最大问题：**AI不知道为什么选择这个方案**。

### 没有决策文档

```
用户: 为什么用RRF而不是加权平均？
AI: 我不知道，可能是某种惯例？
用户: 面试时怎么说？
AI: ...
```

### 有决策文档

```
用户: 为什么用RRF而不是加权平均？
AI: 让我读design.md...

根据design.md Decision 2：

**选择**: RRF融合

**理由**:
- Dense和Sparse分数范围不同（cosine vs BM25）
- 加权平均需要归一化，但归一化方法影响结果
- RRF基于排序而非分数，无需归一化
- k=60是论文验证的稳定参数

用户: 面试时我可以说这些？
AI: 可以，每个决策都有理由。
```

---

## 决策记录格式

```markdown
### Decision N: [决策主题]

**选择**: [具体选择]

**理由**:
1. [理由1 - 为什么好]
2. [理由2 - 解决什么问题]
3. [理由3 - 有什么优势]

**备选方案**:
1. ❌ [方案A] → [为什么放弃]
2. ✅ [方案B] → [为什么选择]
3. ❌ [方案C] → [为什么放弃]
```

### 格式解释

| 部分 | 内容 | 目的 |
|------|------|------|
| **选择** | 最终选了什么 | AI知道要实现什么 |
| **理由** | 为什么选这个 | AI理解选择逻辑 |
| **备选方案** | 为什么不选其他 | AI知道边界 |

## 决策类型示例

### 1. 技术选型决策

```markdown
### Decision: 向量数据库选择

**选择**: Qdrant

**理由**:
1. 开源免费（个人项目成本敏感）
2. Docker一行启动（部署简单）
3. 支持Sparse向量（Hybrid检索必需）
4. HNSW性能好（O(logN)检索）
5. 有云服务选项（未来可扩展）

**备选方案**:
1. ❌ Pinecone → 贵，数据出境，不适合个人项目
2. ❌ Milvus → 复杂，运维重，适合大规模(亿级)
3. ❌ Weaviate → GraphQL接口，本项目不需要
4. ✅ Qdrant → 平衡选型，适合十万级规模
```

面试应用：
> "为什么选Qdrant？因为它开源免费、部署简单、支持Sparse向量、性能好、有云服务选项。如果是企业项目，亿级我会选Milvus，快速落地我会选Pinecone。"

### 2. 架构决策

```markdown
### Decision: 预加载时机

**选择**: HTTP服务器启动后预加载

**理由**:
1. 服务器可立即响应健康检查（Docker/K8s readiness probes）
2. WebSocket可广播加载进度（用户可见进度）
3. 避免服务器启动超时（部署场景）

**备选方案**:
1. ❌ 服务器启动前加载 → 健康检查失败，容器被杀
2. ❌ 并行加载 → 与首次请求竞争资源，可能失败
3. ✅ 服务器启动后加载 → 响应检查，广播进度
```

面试应用：
> "为什么服务器启动后预加载？因为Docker/K8s有readiness probes，如果启动前加载，容器会被认为是'不健康'而重启。启动后加载可以响应健康检查，同时WebSocket广播进度。"

### 3. 参数决策

```markdown
### Decision: RRF参数k值

**选择**: k = 60

**理由**:
1. 论文《Reciprocal Rank Fusion》推荐值
2. 多场景测试表现稳定
3. 无需反复调参

**备选方案**:
1. ❌ k=40 → 敏感度过高，rank权重太大
2. ❌ k=80 → 敏感度过低，融合效果不明显
3. ✅ k=60 → 论文验证，稳定
```

面试应用：
> "为什么k=60？这是论文验证的稳定参数，大多数场景不需要调。如果效果不好，可以尝试调整，但目前表现很好。"

### 4. 算法决策

```markdown
### Decision: 断崖检测阈值

**选择**: similarityThreshold = 0.7, gradientThreshold = 0.15

**理由**:
1. 低于0.7表示相邻内容语义不相关
2. 梯度>0.15验证是真正的断崖而非噪声
3. 经多种文档类型测试表现稳定

**备选方案**:
1. ❌ threshold=0.6 → 过敏感，产生过多分割
2. ❌ threshold=0.8 → 不敏感，语义边界被忽略
3. ❌ gradient=0.1 → 噪声误判
4. ❌ gradient=0.2 → 遗漏真正断崖
5. ✅ threshold=0.7 + gradient=0.15 → 平衡
```

面试应用：
> "阈值怎么选的？这是启发式设计，不是数学推导。低于0.7相似度认为有断崖，但还要验证梯度>0.15防止噪声。这些值经过多种文档测试表现稳定。"

### 5. 实现决策

```markdown
### Decision: SSE Buffer处理

**选择**: 正确处理 `\n\n` 分隔符，保留不完整行

**理由**:
1. SSE协议用双换行分隔消息
2. 单换行后可能还有数据
3. 清空buffer会丢失不完整行

**备选方案**:
1. ❌ buffer = '' → 丢失不完整行
2. ❌ 只处理完整消息 → 等太久
3. ✅ buffer = lines.pop() → 保留不完整行

实现对比：
// ❌ 错误
buffer += decoded;
const lines = buffer.split('\n');
buffer = '';  // 丢失最后一行

// ✅ 正确
buffer += decoded;
const lines = buffer.split('\n');
buffer = lines.pop() || '';  // 保留不完整行
```

## 决策文档化的价值矩阵

| 场景 | 无决策文档 | 有决策文档 |
|------|-----------|-----------|
| **AI实施** | 猜测方案，可能偏 | 读决策，精准实施 |
| **用户面试** | 无法解释为什么 | 每个决策可解释 |
| **新成员学习** | 不知道设计思路 | 理解演进过程 |
| **Bug排查** | 不知设计意图 | 理解原始决策 |
| **技术演进** | 不知道能否替换 | 理解选择依据 |
| **未来AI对话** | 无法引用 | 可引用归档决策 |

## 决策记录最佳实践

### 1. 每个重大选择都要记录

什么算"重大选择"：
- 涉及多个方案可选
- 影响架构
- 影响性能
- 影响用户体验
- 特殊参数值

什么不算：
- 使用标准库函数
- 按惯例命名
- 已有代码模式的延续

### 2. 备选方案要有拒绝理由

不能只写"选择了X"，要写：
```markdown
❌ 方案A → [拒绝理由]
```

拒绝理由可以是：
- 成本问题
- 性能问题
- 兼容性问题
- 复杂度问题
- 不符合场景

### 3. 理由要具体

不要写：
```markdown
**理由**: 性能好
```

要写：
```markdown
**理由**: 
- HNSW索引O(logN) vs 内存线性O(N)
- 十万向量检索从500ms降到15ms
```

### 4. 可以引用外部来源

```markdown
**理由**:
- 论文《Reciprocal Rank Fusion》验证
- bge-m3官方文档推荐
- 个人测试结果：X场景提升30%
```

## 决策变更处理

当决策需要变更时：

### 小变更（参数调整）

在原决策注释修改：
```markdown
### Decision: 断崖检测阈值

**选择**: similarityThreshold = 0.65（原0.7，经测试发现更适合中文）

**理由**: ...
```

### 大变更（方案替换）

新增决策条目：
```markdown
### Decision: 向量数据库选择（更新）

**选择**: 从Qdrant迁移到Milvus

**理由**:
- 数据量达到千万级，Qdrant性能下降
- 需要分布式支持
- 原Qdrant选择适用于十万级，现规模超出

**原选择**: Qdrant（2026-04）
**更新时间**: 2026-06
```

## 面试问答示例

### Q: 你的RAG系统和LangChain有什么区别？

> "LangChain是框架，封装了RAG各个环节。我的项目手写实现，展示对每个环节的理解。
>
> 比如：LangChain语义分块是黑盒调用。我的实现是断崖检测算法：计算相邻embedding相似度、梯度验证消除噪声、宽度滤噪防止误判。
>
> 这展示了我理解'为什么这样切分'，不是'调用什么函数'。如果岗位需要快速落地我会用LangChain，如果需要定制优化我手写实现才能深入调优。"
>
> ——来自 `design.md Decision: 断崖检测算法`

### Q: 为什么用RRF而不是加权平均？

> "这是Hybrid检索的设计决策。
>
> 加权平均的问题：
> - Dense是cosine相似度[-1,1]，Sparse是BM25分数[0,∞]，范围不同
> - 需要归一化，但归一化方法影响结果分布
> - 权重参数需要反复调优
>
> RRF的优势：
> - score = Σ 1/(k + rank)，基于排序而非分数
> - 两种搜索的rank天然可比，无需归一化
> - k=60是论文验证的稳定参数
>
> 这是'实用主义'选择：简单、鲁棒、有效。"
>
> ——来自 `design.md Decision: RRF融合策略`
