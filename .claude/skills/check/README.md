# /check 命令系统使用指南

## 快速开始

`/check` 命令系统提供统一的代码质量检查入口，覆盖从需求评审到代码审查的全流程。

## 命令语法

### 预检
```
/check
```
快速扫描当前工作状态，输出下一步建议。

### 需求六维评审 (必须执行)
```
/check:review [change-name]
```
对 OpenSpec change 文档进行六维度评审，生成加权综合评分。

### 代码检查维度
```
/check:design        # 设计一致性检查
/check:security      # 安全检查
/check:concurrency   # 并发检查
/check:complexity    # 复杂度检查
/check:error         # 错误处理检查
/check:auxiliary     # 辅助检查
/check:code-reviewer # 总体质量评审 (必须执行)
```

### 组合执行
```
/check --all                    # 执行全部7维代码检查
/check:security,concurrency     # 执行指定维度组合
```

## 推荐执行顺序

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         开发流程检查时机                                      │
└─────────────────────────────────────────────────────────────────────────────┘

需求阶段                      实现阶段                      完成阶段
    │                           │                           │
    ▼                           ▼                           ▼
/check:review            /check --all              /check:code-reviewer
   (必须)                   (可选)                     (必须)

六维需求评审              7维代码检查               总体质量评审
```

### 必须执行的检查点

- **需求阶段**: `/check:review` — 需求评审通过后方可进入实现
- **完成阶段**: `/check:code-reviewer` — 总体评审通过后方可合并

## 六维需求评审权重

| 维度 | 权重 | 检查内容 |
|------|------|----------|
| 完整性 | 0.25 | 功能需求、背景、非功能需求、验收标准 |
| 一致性 | 0.20 | 内部矛盾、规范冲突、历史需求冲突 |
| 可追溯性 | 0.15 | 需求来源、命名ID、变更历史 |
| 质量 | 0.20 | 模糊词语、指标量化、可测试性 |
| 模板符合度 | 0.10 | 标准结构、必填章节 |
| 上下文引用 | 0.10 | SOP引用、经验引用、规范引用 |

### 综合得分阈值

| 得分 | 结论 | 行动 |
|------|------|------|
| ≥85 | 通过 | 直接进入实现阶段 |
| 70-84 | 有条件通过 | 修复 Critical 问题后进入实现 |
| 50-69 | 需修订 | 系统性修订后重新评审 |
| <50 | 不通过 | 重新起草需求文档 |

## 报告解读

所有评审报告保存在 `context/review/` 目录，命名格式:
```
YYYY-MM-DD-HHmm-<command>-<target>.md
```

| ... | ... | ... | ... | ... |

## 常见问题

### Q: `/check:review` 和 `/check:code-reviewer` 有什么区别?

A: `/check:review` 评审需求文档（proposal.md, design.md, specs），`/check:code-reviewer` 评审实际代码实现。

### Q: 什么时候应该使用 `/check --all`?

A: 在实现过程中，当完成一批功能或准备提交前，使用 `/check --all` 全面检查代码质量。

### Q: 报告文件可以删除吗?

A: 可以。报告文件用于历史追踪，超过 30 天的旧报告可以手动清理。

### Q: 如果没有 OpenSpec change，还能使用 `/check:review` 吗?

A: `/check:review` 需要有 OpenSpec change 文档。如果没有，可以使用 `/check:code-reviewer` 进行代码评审。

## 模糊词语黑名单

六维评审会检测以下模糊词语:
```
尽量、大概、可能、通常、一般、适当、合理
尽可能、原则上、基本、相对、某种程度上
理想情况下、视情况而定、根据实际情况
```

发现模糊词语时应替换为具体数值或明确表述。
