## Context

当前项目已有多个质量检查相关技能：
- `quality-check`：运行 lint + build + test
- `requesting-code-review`：派遣子代理进行代码审查
- `verification-before-completion`：完成前验证原则
- `chinese-code-review`：中文代码审查规范

这些技能分散在不同入口点，缺乏统一调度和系统性评审流程。需求文档评审完全缺失，导致需求阶段问题流入实现阶段。

技术约束：
- 技能系统使用 Markdown 格式定义
- 子代理通过 Agent 工具调用，使用 general-purpose 类型
- 报告持久化需要项目级目录 `context/review/`

## Goals / Non-Goals

**Goals:**
- 提供统一的 `/check` 命令入口，支持多子命令
- 实现六维需求评审（完整性、一致性、可追溯性、质量、模板符合度、上下文引用）
- 实现七个代码检查维度（设计、安全、并发、复杂度、错误、辅助、总体评审）
- 支持组合执行模式（`/check --all` 或指定维度组合）
- 实现报告持久化到 `context/review/` 目录
- 定义必须执行的检查点规则

**Non-Goals:**
- 不修改现有 quality-check、requesting-code-review 等技能
- 不实现自动化触发（仅在用户主动调用时执行）
- 不实现跨项目共享的评审历史数据库
- 不实现评审结果的自动化修复

## Decisions

### D1: 单 Agent 内部并行处理 vs 多 Agent 并行调度

**决策：** 使用单 Agent 内部并行处理模式

**理由：**
- 减少 API 调用次数（1 次 vs 7 次）
- 共享文档上下文，避免重复加载
- 简化输出合并逻辑
- 统一超时控制

**替代方案：** 多 Agent 并行调度
- 优点：完全并行，可分别设置超时
- 缺点：高 API 成本，上下文重复加载，输出合并复杂
- 结论：放弃，性价比不足

### D2: 报告持久化位置

**决策：** 持久化到 `context/review/` 目录

**理由：**
- 项目级目录，易于清理和追踪
- 与 OpenSpec 的 `openspec/changes/` 目录分离，避免污染
- 文件命名 `<timestamp>-<command>-<target>.md` 便于历史排序

**替代方案：** 
- A) 写入 `openspec/changes/<name>/review-report.md`
  - 缺点：与 OpenSpec change 目录耦合，非 OpenSpec 项目无法使用
- B) 写入 `.claude/reports/`
  - 缺点：隐藏目录，用户不易发现
- 结论：选择 `context/review/`，显式且独立

### D3: 子命令分类和必须执行规则

**决策：**
- `/check:review` — 需求评审（必须执行，独立）
- `/check:code-reviewer` — 总体评审（必须执行，独立）
- 其他 7 个子命令 — 可选执行，支持组合

**理由：**
- 需求阶段和完成阶段是关键质量门禁点
- 中间实现阶段的检查可按需执行
- 组合执行提高效率（`/check --all` 一次完成 7 维检查）

### D4: 六维需求评审权重分配

**决策：**
| 维度       | 权重 | 理由                             |
|------------|------|----------------------------------|
| 完整性     | 0.25 | 最关键，缺失需求导致实现偏差      |
| 一致性     | 0.20 | 关键，矛盾需求导致实现混乱        |
| 质量       | 0.20 | 关键，模糊需求导致歧义理解        |
| 可追溯性   | 0.15 | 基础，便于后续追踪和变更          |
| 模板符合度 | 0.10 | 格式，影响可读性                  |
| 上下文引用 | 0.10 | 可信度，影响决策依据              |

**综合得分阈值：**
- ≥85：通过，可直接进入实现阶段
- 70-84：有条件通过，需修复 Critical 问题
- 50-69：需修订，系统性修订后重新评审
- <50：不通过，重新起草需求文档

### D5: 报告文件命名格式

**决策：** `YYYY-MM-DD-HHmm-<command>-<target>.md`

**示例：**
- `2026-04-22-1530-precheck-default.md`
- `2026-04-22-1530-review-agent-planning.md`
- `2026-04-22-1530-all-code-review.md`

**理由：**
- 时间戳前缀便于历史排序
- 命令标识便于区分检查类型
- 目标识便于区分检查对象

## Risks / Trade-offs

### R1: 单 Agent 模式的超时风险

**风险：** 组合执行时（7 维检查）可能因单 Agent 超时导致部分检查未完成

**缓解：**
- 设置合理的超时时间（建议 300s）
- Agent 内部优先处理高风险维度（security、concurrency）
- 输出格式包含维度完成状态，便于识别未完成项

### R2: 报告持久化目录管理

**风险：** `context/review/` 目录可能积累大量报告文件

**缓解：**
- 文件命名包含时间戳，便于按时间清理
- 建议：用户可定期清理超过 30 天的旧报告
- 未来可考虑添加自动清理机制

### R3: 六维评审的 AI 判断可靠性

**风险：** AI 对"模糊词语"、"指标量化"等判断可能不稳定

**缓解：**
- 定义明确的检测规则（模糊词语黑名单）
- 使用 WHEN-THEN 格式确保可测试性
- 输出包含具体文件位置引用，便于人工验证

### R4: 与现有技能的冲突

**风险：** 用户可能混淆 `/check` 和 `/quality-check`

**缓解：**
- 预检报告明确建议下一步操作
- 文档说明技能定位差异
- `/check:auxiliary` 部分功能与 `quality-check` 类似，但不重复执行

## Migration Plan

无迁移需求。新技能为可选使用，不影响现有流程。

部署步骤：
1. 创建 `.claude/skills/check/` 目录
2. 创建 10 个技能文件
3. 创建 `context/review/` 目录
4. 验证技能加载（通过 `/check` 调用测试）
