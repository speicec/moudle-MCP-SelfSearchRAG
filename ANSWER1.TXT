  ---
  What This Project Is

  This is an Enhanced RAG MCP Server — a medical-domain RAG system exposed as an
   MCP (Model Context Protocol) server so that Claude (or other AI assistants)
  can ingest documents, search them, and get AI-generated answers backed by
  evidence. It has its own Web UI for human operators.

  ---
  1. Document Ingestion Pipeline

  When a document (PDF, image) is uploaded, it flows through a 5-stage pipeline
  orchestrated by the Harness:

  Document → [INGEST] → [PARSE] → [CHUNK] → [EMBED] → [INDEX]
                │           │          │          │          │
                ▼           ▼          ▼          ▼          ▼
           Validator    PDF.js    Semantic   BGE-M3    Qdrant
           + Queue      VLM OCR   Chunker    Hybrid    (Dense+
                        Tables    Quality    (1024d)   Sparse)
                        Formulas  Filter

  Each stage emits WebSocket events (stage:start, stage:complete, chunk:created)
   so the frontend shows real-time progress.

  Key details:
  - PDF parsing: pdfjs-dist + VLM for images/tables/formulas
  - Semantic chunking: similarity-cliff detection finds natural boundaries
  - Hybrid embedding: BGE-M3 model produces Dense (1024d) + Sparse vectors
  - Hierarchical chunks: small chunks → parent chunks (small-to-big retrieval)
  - Quality filter: scores chunks on info density, repetition ratio, semantic
  completeness, document relevance

  3. How Retrieval Works

  The EnhancedRetrievalPipeline (src/retrieval/enhanced-retrieval-pipeline.ts)
  is a 7-stage flow:

  Query → [1.Analyzer] → [2.Rewriter] → [3.Decomposer] → [4.Expander]
                                                                │
                                                                ▼
                                                       [5.Retriever]
                                                       (small-to-big
                                                        multi-query)
                                                                │
                                                                ▼
                                                       [6.Reranker]
                                                       hybrid: local
                                                       model or confidence
                                                       calculator
                                                                │
                                                                ▼
                                                       [7.Assembler]
                                                       → Context

  Key design decisions:
  - Small-to-big retrieval: first finds small chunks, then expands to parent
  chunks
  - RRF fusion: merges dense + sparse results with Reciprocal Rank Fusion
  - Hybrid reranker: uses a local cross-encoder for ≤20 results, falls back to
  confidence scoring for larger sets
  - Dynamic topK: adjusts based on average parent chunk token length

  4. How Evaluation Works

  This is the most sophisticated part. The evaluation system has 3 layers × 8 
  dimensions:

  ┌───────────────────────────────────────────────────┐
  │              EVALUATION FRAMEWORK                  │
  ├───────────────────────────────────────────────────┤
  │ Layer 1: 基础 RAGAS                                │
  │   • faithfulness (忠实度)                          │
  │   • contextRelevance (上下文相关性)                 │
  │   • answerRelevance (答案相关性)                    │
  ├───────────────────────────────────────────────────┤
  │ Layer 2: 医疗核心                                  │
  │   • medicalAccuracy (医疗准确性)                    │
  │   • safetyAssessment (安全评估)                     │
  ├───────────────────────────────────────────────────┤
  │ Layer 3: 医疗增强                                  │
  │   • evidenceTraceability (证据可追溯性)             │
  │   • completeness (完整性)                           │
  │   • terminologyAccuracy (术语准确性)                │
  └───────────────────────────────────────────────────┘

  Evidence evaluation (GRADE system)

  Every retrieved source is graded:
  - Literature type: RCT > Meta-analysis > Guideline > Observational > Case
  Report > Expert Opinion
  - Grade A/B/C/D: based on type, recency, authority, consistency
  - Overall evidence grade computed across all sources

  Recall evaluation tests

  src/__tests__/recall-evaluation.test.ts tests recall@k against known
  query-answer pairs with Chinese medical/technical documents. This directly
  measures retrieval quality.

  ---
  Key Architectural Insights

  1. Plugin architecture: Pipeline stages are composed of plugins, registered
  via PluginRegistry. This makes the system extensible.
  2. Hybrid embedding strategy: Dense (semantic) + Sparse (keyword) vectors
  stored in Qdrant, fused via RRF — combines the best of both worlds.
  3. Medical domain specialization: Custom dictionaries for diseases, drugs,
  indicators; GRADE evidence evaluation; safety layer for contraindication
  detection.
  4. Evaluation is built-in: Not an afterthought — every agent query
  automatically triggers evaluation, and results are persisted + broadcast in
  real-time.
  5. Dual-mode agent: ReAct loop for simple queries, Planning+DAG for complex
  multi-step medical reasoning.

  MedicalEvaluationPipeline 对每次查询调用 LLM
  8次（8个维度各一次）。默认配置用的是 deepseek-reasoner，retry=3。如果加上
  Planning 模式的 LLM 调用，一条查询可能触发 10+ 次 LLM 调用。

  3. Redis 是可选依赖

  有 Redis → 评估进队列 → Worker 异步处理 → 不阻塞主请求
  无 Redis → 评估同步执行 → 仍不阻塞HTTP响应(但占用主线程)

  即使 Redis 挂了，系统降级为同步模式，不会丢失评估能力。

  4. WebSocket 事件粒度

  Agent 执行过程中发射的事件序列：
  agent:input → agent:entities → agent:complexity → agent:mode
  → agent:query_rewrite → agent:template? → agent:dag?
  → agent:execution (多次) → agent:complete
  → evaluation:complete (异步, 稍后到达)

  前端可以逐帧展示 Agent 的思考过程，就像看一个医生的诊断过程。

  为什么不是 BM25？

  项目的 Sparse 向量来自 BGE-M3 模型内置的稀疏输出，不是传统的 BM25 统计算法：

  // hybrid-embedding-service.ts 第451行注释:
  // "This provides BM25-style sparse vectors for keyword matching"
  //
  // BGE-M3 在训练时学到了哪些词对检索重要
  // 输出的 sparse vector 是 {term_index: weight} 的映射
  // 效果类似 BM25（关键词匹配），但是学习出来的，不是统计出来的

  代码里 rrf-fusion.ts 变量名叫 sparseScore，注释写的是 "Original Sparse BM25
  score"——这只是概念上的类比，实际计算的是 BGE-M3 的 sparse embedding 在 Qdrant
  里的检索分数。

  对比一下

                  BM25                    本项目 Sparse
  来源           统计算法 (TF-IDF变体)      BGE-M3 神经网络学习
  计算位置        应用层                    模型内部
  词权重          IDF 统计                  训练得到的 attention 权重
  维度            词表大小                  词表大小 (term index map)
  优势            可解释、无模型依赖          与 Dense 同模型，语义+关键词一体
  劣势            需要分词、调参             依赖模型质量

  意图识别不是单一模块，而是三个独立系统在不同阶段协作：

  第 0 层：QueryAnalyzer（检索管线内部）

  QueryAnalyzer.analyze(query)
      │
      ├─→ 快速路径 (不用 LLM):
      │     detectFilters(query)  → 正则提取年份、月份、类别
      │     heuristicComplexity(query) → 规则判断:
      │       "对比/比较/区别" → complex
      │       "2023年/第3章" → structured
      │       "怎么/如何/为什么/多个?" → complex
      │       长度 > 50 → complex

      │
      │     如果 simple + 无filter → 直接返回，不调 LLM
      │
      ├─→ LLM 路径 (complex 或 structured):
      │     ANALYSIS_PROMPT_TEMPLATE 发送给 LLM:
      │     "分析以下查询: 复杂度、是否需要分解、是否需要重写、
      │      检测的过滤条件、建议子查询、重写后查询"
      │     → 解析 LLM JSON → 得到 QueryAnalysisResult
      │
      └─→ 有缓存 (Map<string, QueryAnalysisResult>), TTL 可配置

  rewrite/decompose/expand。这是检索策略层面的意图识别。

  第 1 层：EntityRecognizer（词典匹配）

  extractMedicalEntities(query)
      │
      ├─→ matchDiseases(query)
      │     遍历 ALL_DISEASES 词典 (疾病名称 + 别名)
      │     indexOf() 字符串匹配
      │     → [{ matchedTerm: "2型糖尿病", entityId: "disease_dm2", ... }]
      │
      ├─→ matchDrugs(query)
      │     遍历 ALL_DRUGS (降糖药 + 降压药 + 甲状腺药)
      │     匹配: canonicalName / aliases / brands
      │     → [{ matchedTerm: "二甲双胍", entityId: "drug_metformin", ... },
      │        { matchedTerm: "氨氯地平", entityId: "drug_amlodipine", ... }]
      │
      └─→ matchIndicators(query)
           遍历 ALL_INDICATORS (血糖/血压/血脂/肾功能等)
           → [] (这个查询里没有)

      最终: confidence = matchedCount / totalDictionarySize 的变体

  作用:
  识别出"这个查询在问什么病、什么药、什么指标"。这是医学领域的实体级意图识别。

  第 2 层：IntentAnalyzer（规则化意图分类）

  analyzeIntent(entities, query)

      │
      ├─→ predictRetrievalNeeds()
      │     safety_check → 所有实体 required
      │     comparison → primary required, secondary recommended

  作用: 决定"这个查询是什么类型、需要重点搜什么、要不要检查药物相互作用"。这是任
  务级的意图识别。

  第 3 层：ComplexityJudge（决定走 ReAct 还是 Planning）

  assessComplexity(entities, query)
      │
      │ 规则优先级 (从高到低):
      │
      ├─→ detectYearFilter()      → structured, needsPlanning=true
      ├─→ detectSafetyIntent()    → structured, needsPlanning=true
      ├─→ detectDrugRecommend()   → moderate, needsPlanning=true
      ├─→ entityCount<=1 + noCmp  → simple, needsPlanning=false ← 走 ReAct
      ├─→ hasComparison           → complex, needsPlanning=true
      ├─→ entityCount 2-3         → moderate, needsPlanning=true
      └─→ otherwise               → complex, needsPlanning=true

  作用: 最终决定 Agent 的执行模式。
